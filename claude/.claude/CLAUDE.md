# Context & Token Discipline

Every tool call resends the whole growing conversation, so verbose or repeated output compounds fast. This section exists because a session doing genuinely small work (config edits, a few debugging fixes) burned ~250k tokens - traced back to avoidable patterns below, not to the actual work.

## Suppress repeated/verbose output
- Don't re-dump output you've already seen unchanged. Re-running `dotnet build`/`npm run build`/etc. to check for *new* errors? Grep for `error`/`Error(s)` instead of re-printing the same pre-existing warning list every time.
- Before broad recursive commands (`find`, `ls -R`, `grep -r`), scope the path and exclude build artifacts (`bin/`, `obj/`, `node_modules/`, `.git/`) up front - don't dump everything and filter after.
- Tail/grep container and CI logs for the relevant window, not the full scrollback.

## Cap debugging breadth
- Infra/networking issues (ports, containers, DNS): if 3-4 diagnostic commands haven't found root cause, stop adding more tools one at a time (`ss` then `ps` then `/proc` then `ip netns`...). State the current hypothesis explicitly and test *that* directly, or ask the user, instead of escalating breadth.
- One well-scoped repro beats several small exploratory pokes.

## Batch, don't trickle
- Combine related read-only checks into one Bash call (`cmd1; echo ---; cmd2`) instead of one tool call per check - each separate call resends the full transcript so far for no new info.

## Screenshots / headless browser
- Use the fewest screenshots that answer the question. Prefer reading `getComputedStyle`/DOM state directly over eyeballing multiple screenshots when checking CSS/layout behavior. See the Playwright / Browser Use section below for how to actually drive a browser.

## Say it out loud
- If several tool calls have passed without landing the fix (i.e. still gathering info, not converging), say so to the user rather than silently continuing to iterate.

## CRITICAL: New Files Must Be Git-Tracked

**Before running `rebuild`, any NEW files must be added to git:**
```bash
git add path/to/new/file
```

Nix uses a flake that only sees git-tracked files. If you create a new file (script, config, etc.) and run `rebuild` without `git add`, you'll get:
```
error: Path 'path/to/file' in the repository is not tracked by Git.
```

**Workflow for adding new files to nix config:**
1. Create the file
2. `git add path/to/new/file` (stage it)
3. `rebuild` (now nix can see it)
4. Test
5. Commit when ready

# Playwright / Browser Use

Browsers are provided system-wide via home-manager (`pkgs.playwright-driver.browsers`, see `nix/modules/shared/home-packages.nix`), with `PLAYWRIGHT_BROWSERS_PATH` and `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` set globally. **Never run `playwright install`/`bunx playwright install`/`npx playwright install`** anywhere, ever - downloading is disabled on purpose and that command will just fail. There is always a working path that needs no install; use it instead of reaching for `install`:

**Decision tree - where to run Playwright from:**
1. **Project already has `playwright`/`@playwright/test` as a devDependency** (check `package.json` - most Angular/e2e projects here do): use that project's own install and config as-is. If it errors with a browser-version mismatch, its pinned `playwright` version has drifted from the nixpkgs `playwright-driver` revision - fix the *version pin* (or bump the `nixpkgs` flake input), don't install browsers.
2. **No project involved / ad hoc check** (e.g. "does this dev server render correctly", "click through this flow"): use `nix/scripts/browser-scratch/` - a git-tracked, version-pinned scratch project that always matches the installed browser revision. `cd` there, `bun install` once (installs the JS package only, no download), then copy `example.mjs`'s pattern into a throwaway script. See its README for the full explanation and how to re-pin after a `nixpkgs` bump.

**Keep it fast and cheap on tokens** (real-world reports put a naive MCP-style loop at ~100K+ tokens for an 8-step flow vs ~25K for the pattern below):
- Prefer targeted reads over screenshots: `page.locator(...).innerText()`, `getComputedStyle`, `page.title()`. These cost a few hundred bytes; a screenshot costs thousands of tokens even before you look at it.
- Only take a screenshot when a genuinely visual judgment is needed (layout, colors, rendering glitches) - and scope it to the viewport, not full-page, unless full-page is the point.
- Save screenshots to disk and view via the Read tool rather than piping image bytes through intermediate steps.
- Batch a whole flow (navigate, fill, click, read result) into one script run instead of one tool-call per action.
- Always `browser.close()` when done.

# Git Conventions

## Branch Naming
```
TYPE/TICKET_ID-short-description
```
Examples:
- `feat/12345-add-dark-mode`
- `bug/12346-fix-login-redirect`
- `hotfix/12348-critical-auth-fix`
- `chore/12347-cleanup-dependencies`

Types: `feat`, `bug`, `hotfix`, `chore`

## Commit Messages
```
#TICKET_ID TYPE(component): description
```
Examples:
- `#12345 feat(consumption): add hydrological calendar support`
- `#12346 bug(auth): resolve login redirect loop`
- `#12347 chore(deps): update angular to v19`

**No ticket ID:** omit the `#TICKET_ID` prefix entirely - do NOT use `#0` or any other placeholder. Format becomes just `TYPE(component): description`.

Types: `feat`, `bug`, `chore` (hotfix branches use `bug` in commit)

## Lazygit Workflow

The user uses lazygit for git operations. Key commands:
- **`o`** on a commit/branch: Opens in Azure DevOps browser (creates PR or views commit)
- **`P`**: Push to remote
- **`p`**: Pull from remote
- **`c`**: Commit staged changes

When the user says "press o in lazygit", they're opening the branch/commit in Azure DevOps to create a Pull Request.

## Creating PRs with Azure DevOps CLI

PRs go to `dev` branch. Always create a feature/bug branch first:

```bash
# 1. Create and push branch
git checkout -b bug/TICKET_ID-description
git push -u origin bug/TICKET_ID-description

# 2. Create PR
az repos pr create \
  --repository CustomerPortal.Angular \
  --source-branch bug/TICKET_ID-description \
  --target-branch dev \
  --title "#TICKET_ID bug(component): description" \
  --description "## Summary
- What was fixed/added

## Test plan
- [ ] Test steps"

# 3. Link work item (required!)
az repos pr work-item add --id PR_ID --work-items TICKET_ID
```

# Jujutsu (jj) - Preferred Over Git

**IMPORTANT:** When a repo has jj initialized (`.jj/` directory exists), prefer jj commands over git.

## Why jj Over Git

- **Auto-commit**: Working copy is always tracked, impossible to lose work
- **Undo anything**: `jj undo` reverses any operation
- **Lock-free parallel**: Multiple workspaces on same repo simultaneously
- **Git-compatible**: Full interop, `jj git push` works with GitHub/Azure DevOps

## Detecting jj Repos

```bash
# Check if jj is initialized
if [ -d ".jj" ]; then
  echo "Use jj commands"
else
  echo "Use git commands"
fi
```

## jj Command Reference

| Git Command | jj Equivalent | Notes |
|-------------|---------------|-------|
| `git status` | `jj status` | Shows working copy changes |
| `git log` | `jj log` | Shows commit graph |
| `git add . && git commit -m "msg"` | `jj describe -m "msg"` | Working copy auto-tracks |
| `git checkout -b branch` | `jj new -m "description"` | Creates new change |
| `git branch branch-name` | `jj bookmark create branch-name` | Bookmarks are jj's branches |
| `git push origin branch` | `jj git push --bookmark branch` | Push specific bookmark |
| `git pull` | `jj git fetch && jj rebase -d main@origin` | Fetch + rebase |
| `git diff` | `jj diff` | Show changes |
| `git stash` | Not needed | Working copy is always a commit |

## jj PR Workflow

```bash
# 1. Start work (already on main)
jj new -m "feat: add login page"

# 2. Make changes... (auto-tracked, no git add needed)

# 3. Create bookmark (branch) for PR
jj bookmark create feat/12345-add-login

# 4. Push bookmark
jj git push --bookmark feat/12345-add-login

# 5. Create PR via CLI
az repos pr create \
  --source-branch feat/12345-add-login \
  --target-branch dev \
  --title "#12345 feat(auth): add login page"

# 6. If PR needs changes
jj edit <change-id>  # Go back to that change
# Make fixes...
jj git push --bookmark feat/12345-add-login  # Force-pushes automatically
```

## Common jj Patterns

```bash
# See what I'm working on
jj log

# Update commit message
jj describe -m "better message"

# Undo last operation (SAFE - works for anything)
jj undo

# Split current change into multiple commits
jj split

# Squash into parent
jj squash

# Rebase onto latest main
jj git fetch
jj rebase -d main@origin
```

## When to Still Use Git

- Repo doesn't have `.jj/` initialized
- Complex merge conflict resolution (jj defers conflicts)
- Team requires specific git workflow
